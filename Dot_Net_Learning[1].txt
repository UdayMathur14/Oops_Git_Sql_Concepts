🧱 1. ADO.NET – (Manual tareeka)
ADO.NET ka matlab hai ActiveX Data Object for .NET.
Isme tum:

Khud connection banate ho
Query likhte ho (SELECT, INSERT, UPDATE, DELETE)
Command chalate ho

📝 Kya yaad rakho:
Tumhe query khud likhni padti hai.

Fast performance, zyada control deta hai.
Lekin thoda lamba code ho jata hai.

🧱 1. Entity Framework (EF) — Database ko .NET se connect karne ka bridge
EF ek ORM (Object Relational Mapper) hai.
Iska kaam hota hai tumhare database ko C# objects me convert karna.
Tumhe manually SELECT * FROM Table jaisi queries nahi likhni padti.
Tum direct C# class ke object ke through data access kar sakte ho.

📝 Kya yaad rakho:

Tumhe queries kam likhni padti hai (LINQ ka use hota hai).
Maintain karna asaan hai.
Fast development ke liye best hai.
Lekin performance kabhi kabhi ADO.NET se kam hoti hai.
✅ Best jab tum CRUD operation fast banana chahte ho bina zyada query likhe.

| **Feature**          | **ADO.NET 🧱**                                                     | **Entity Framework 🚀**                                                  

| **Query Writing**    | Manual SQL queries likhne padte hain (`SELECT * FROM ...`)         | LINQ ya lambda expressions se query likhte ho (ORM handle karta hai SQL) |

| **Development Time** | 🕒 Zyada — manually query likhni aur mapping karni padti hai       | 🕒 Kam — auto mapping aur CRUD generation hoti hai                       |
| **Suitable For**     | 🧩 Complex logic, stored procedures, performance-critical apps     | 🚀 Rapid development, CRUD-based apps                                    |
| **Code Size**        | 🧾 Lamba — boilerplate code zyada                                  | Chhota — EF zyada code generate kar deta hai                          |

ADO.NET = Manual car (tum clutch + gear khud handle karte ho) — full control, better performance.
Entity Framework = Automatic car (system gear change karta hai) — easy driving, thoda less control.

🌐 REST API vs HTTP Methods
🔸 REST API - 
it’s a set of architectural principles or rules that define how APIs should be designed
so that they are simple, scalable, and standard.

Sets the rules and structure for how data will be sent, received, and represented.
⚙️ 6 Core Principles of REST
1️⃣ Client–Server Architecture
The client (like a web app or mobile app) and the server (API/backend) are separate.

Client only sends requests and shows data; server handles business logic and data storage.
👉 This separation makes the system more flexible and maintainable.

2️⃣ Statelessness
Each API request should contain all the information needed to process it.
Server does not remember any previous request (no session data).
👉 Every request is independent.
Example:
If you send a request to /api/customers/1, it must include your token or credentials each time.

3️⃣ Cacheable
Responses from the server can be cached by the client or intermediate systems to improve performance.
👉 If data doesn’t change frequently, caching avoids repeated API calls.

4️⃣ Uniform Interface
All REST APIs should follow a consistent way of interacting (URLs, methods, responses).
For example:
Use GET for fetching, POST for creating, etc.

Use clear URLs like /api/products/1
👉 It keeps the API predictable and easy to use.

5️⃣ Layered System
REST APIs can have multiple layers (client → API gateway → service → database).
The client doesn’t need to know how many layers exist.
👉 Improves scalability and security.

6️⃣ Code on Demand (Optional)

Server can send executable code (like JavaScript) to the client to extend its functionality.
👉 This is optional and rarely used.

🔹 HTTP Methods

HTTP methods are actions or verbs used inside REST APIs to perform operations.
They tell what you want to do with the resource — like read, create, update, or delete.
Common HTTP Methods:
GET → Read data
POST → Create data
PUT → Update data
DELETE → Remove data
Each HTTP method represents a single type of request to the server.


🔁 Relation Between Them
REST API is the architecture (the system).

HTTP Methods are the actions used inside REST APIs.
In short:

REST API = “What resource to expose”
HTTP Method = “What action to perform on that resource”

Dependency Injection (DI)

Dependency Injection (DI) is a design pattern where an object’s dependencies are injected instead of being created inside the object itself.

Without DI:

public class EmailService {
    public void SendEmail(string message) {
        Console.WriteLine($"Sending: {message}");
    }
}

public class Notification {
    private EmailService _emailService = new EmailService(); // tightly coupled

    public void Notify(string msg) {
        _emailService.SendEmail(msg);
    }
}


Here, Notification depends directly on EmailService.
If you want to change the way emails are sent (like via SMS), you’d have to modify this class.


With DI:

public interface IMessageService {
    void Send(string message);
}

public class EmailService : IMessageService {
    public void Send(string message) {
        Console.WriteLine($"Sending email: {message}");
    }
}

public class Notification {
    private readonly IMessageService _messageService;

    public Notification(IMessageService messageService) {
        _messageService = messageService;
    }

    public void Notify(string msg) {
        _messageService.Send(msg);
    }
}


Now you can easily switch to SMS, push notifications, etc., without changing the Notification class.

| Service       | Work                                   | Lifetime      |
| ------------- | -------------------------------------- | ------------- |

Transient: When you want a fresh instance every time (e.g., utility, calculation service).
Scoped: When you want one instance per request (e.g., database operations).
Singleton: When state/data can be safely shared globally (e.g., caching, logging).

🧠 What is Asynchronous (Async) Programming?

Async programming means running tasks without blocking the main thread — so your program can do other work while waiting for something slow (like a database call, API request, or file I/O) to finish.
It is used for :
🚀 Performance	Lets your app handle more work at the same time.
💻 Responsive UI	UI apps (like WPF/WinForms) don’t freeze while waiting.
🌐 Efficient Servers	Web APIs (like ASP.NET Core) can serve more users with fewer threads.
🔄 Non-blocking I/O	Perfect for DB calls, HTTP requests, or reading files.

⚠️ Important Notes

Async does not make code run faster — it just uses resources more efficiently.
Use async/await mainly for I/O-bound work (DB, API, File I/O) — not for heavy CPU tasks.

✅ Bonus Interview Tip

If asked:
"What happens to the thread when you call an async method?"
Say:
“Async methods don’t create new threads. They use the same thread until the first await. 
After that, the thread is released, and the rest of the method continues on a thread from the thread pool once the awaited operation completes.”

2. What is the difference between IEnumerable and IQueryable?


| Term              | Meaning                                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| **`IEnumerable`** | Used for **in-memory** collections (like List, Array, etc.). Works in C# (client side).                    |
| **`IQueryable`**  | Used for **remote data sources** (like SQL Server, via Entity Framework). Works in database (server side). |

| Feature            | `IEnumerable`                | `IQueryable`          |
| ------------------ | ---------------------------- | --------------------- |

| Deferred Execution | Yes                          | Yes                   |
| Namespace          | `System.Collections.Generic` | `System.Linq`         |
| Use with EF Core   | Not recommended              | Recommended           |

6. What is an extension method in C#?
An Extension Method is a special static method that lets you add new functionality to existing classes
👉 without modifying their original code or creating a derived class (inheritance).
You can “extend” an existing class from outside it.

Extension method = Add new method to an existing class without modifying it.
public class Student
{
    public string Name { get; set; }
}
Now you want to add a new function SayHello() to it —
but you cannot edit the Student class (maybe it’s from another library).

So you create an extension method 👇

✅ Step 1 – Create a static class
csharp
Copy code
public static class MyExtensions
{
    // 'this' tells C# that it's an extension method for Student class
    public static void SayHello(this Student student)
    {
        Console.WriteLine($"Hello, {student.Name}!");
    }
}
✅ Step 2 – Use it like a normal method
csharp
Copy code
class Program
{
    static void Main()
    {
        Student s = new Student();
        s.Name = "Uday";

        s.SayHello();   // 👈 calling the new function
    }
}
🧾 Output:

Copy code
Hello, Uday!

Current pattern used:
Sometimes people call this pattern:
N-Tier Architecture
or Layered Pattern


| Feature                                                     | **POST**                                                              | **PUT**                                                                             |
| ----------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Purpose**                                                 | To **create** a new resource                                          | To **update** an existing resource (or replace it)                                  |
| **Idempotent (same request multiple times = same result?)** | ❌ **Not idempotent** — calling POST twice will create **two records** | ✅ **Idempotent** — calling PUT twice will **update the same record**, no duplicates |
| **Typical usage**                                           | `/api/users` → create a new user                                      | `/api/users/5` → update user with ID 5                                              |
| **Request body**                                            | Contains new data for creation                                        | Contains full data of the resource to update                                        |
| **Server response**                                         | Usually returns `201 Created` with the new resource info              | Usually returns `200 OK` or `204 No Content` after successful update                |
| **Creates new resource?**                                   | ✅ Yes                                                                 | 🚫 No (unless you allow “upsert”, but rare)                                         |




✅ In Simple Words

HTTP → “Talks openly” — anyone on the network can read or modify data.

HTTPS → “Talks secretly” — data is encrypted before sending.

Example:

http://example.com/login     ❌ Password visible in network sniffers
https://example.com/login    ✅ Password encrypted and safe

| Feature             | **HTTP**                                                          | **HTTPS**                                                             |
| ------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Full form**       | HyperText Transfer Protocol                                       | HyperText Transfer Protocol **Secure**                                |
| **Port**            | 80                                                                | 443                                                                   |
| **Security**        | ❌ Data is sent in **plain text** (can be intercepted by hackers). | ✅ Data is **encrypted** using **SSL/TLS**, keeping it private.        |
| **Data Protection** | None — vulnerable to sniffing, tampering.                         | Protects data from **man-in-the-middle attacks**.                     |
| **Certificate**     | No SSL certificate needed.                                        | Requires an **SSL/TLS certificate** issued by a trusted authority.    |
| **Speed**           | Slightly faster (no encryption overhead).                         | Slightly slower (encryption + decryption), but almost negligible now. |
| **SEO & Trust**     | Not preferred by browsers; shows “Not Secure” warning.            | Preferred; improves **SEO ranking** and user trust.                   |
